_In this post, I’ll be analyzing a variant of Lumma Stealer—a well-known and constantly evolving information stealer. But I’m not doing this with just the usual static and dynamic tools. Instead, I’m exploring how AI, when connected through the Model Context Protocol (MCP), can become a powerful collaborator in reverse engineering._

_All of this takes place in my home lab, where I use tools like Ghidra, Volatility, Regshot, Procmon, and more. But the real game-changer is the integration of Claude AI with Ghidra using GhidraMCP—a plugin developed by LaurieWired (https://github.com/LaurieWired/GhidraMCP) that transforms Ghidra into an AI-assisted reverse engineering platform_

GhidraMCP works by exposing live disassembly and decompiled views to the AI through MCP, allowing it to interpret functions, track data flows, and help reason about control structures. Instead of just asking the AI generic questions, I can now ask:
What does this obfuscated function likely do, based on its control flow and API calls?” and get responses that are grounded in real binary context.



## [](#header-3) So what is MCP exactly?

AI has come a long way—it can write, code, explain, and even reverse engineer. But one of the most exciting improvements lately is its ability to talk directly to other tools. That’s where Model Context Protocol (MCP) comes in.

MCP creates a bridge between AI systems and the tools or data they need. Here’s how it works in simple terms:
MCP Hosts are tools like Claude Desktop, IDEs, or any AI that wants to interact with your system.
MCP Servers are small programs that unlock specific abilities—like letting the AI read files, analyze memory, or control Ghidra.
MCP Clients manage the communication between the host and these servers, creating 1:1 channels.
Local Resources are things on your own machine (files, memory, databases) that the AI can securely access.
Remote Resources are things online—like APIs or external services—that MCP servers can reach out to.

I’ll walk through how I used this human–AI collaboration to analyze Lumma Stealer—from static analysis in Ghidra with using ghidraMCP, to runtime behavior monitoring with tools like ProcMon. The goal isn’t to replace the analyst—but to show how much more efficient, insightful, and enjoyable reverse engineering can be when you have AI contextually aware of the binary you're working on.

### Dynamic API Resolution

One of the most significant obfuscation techniques used by this malware is its dynamic API resolution mechanism through a hash-based lookup. This occurs in the function `FUN_0044acc0`:
// [... function returns address of resolved API ...]

This function implements a rolling hash algorithm where:
1. Initial hash value is set to `0x275ac351`
2. Each character of the API name is XORed with the current hash value
3. The result is multiplied by `0x8282842b`

In function `FUN_0040d840()`, this resolution mechanism is used extensively to populate a table of API function pointers:

### Control Flow Obfuscation

The malware implements sophisticated control flow obfuscation similar to techniques described in the Google Threat Intelligence analysis of LummaC2 (https://cloud.google.com/blog/topics/threat-intelligence/lummac2-obfuscation-through-indirect-control-flow/). In function `FUN_0040e780`, we see a classic example of this obfuscation pattern:

<img width="500" alt="1" src="https://github.com/user-attachments/assets/4ebb3a28-b8c9-472a-9314-18db519c2c28">

This pattern follows the "dispatcher block" technique where:
1. A series of operations manipulate memory or registers
2. An API function is dynamically resolved via hash
3. The resolved function is called indirectly
4. The process repeats with another function resolution and call

This technique effectively breaks the normal linear control flow, making it extremely difficult for analysis tools to determine function boundaries and relationships.

### FLOSS Findings: Static String and Capability Extraction
To extract embedded and obfuscated strings, I used FLOSS (FireEye Labs Obfuscated String Solver). This tool proved crucial in surfacing both static and dynamically constructed strings, many of which align with known LummaC2 stealer capabilities


**C2 Infrastructure Indicators**
FLOSS identified two decoded strings clearly pointing to external infrastructure:
```
upmodini[.]digital/gokk
soursopsf[.]run/gsoiao
```

`steamcommunity[.]com/profiles/76561199845513035` - Likely a fake Steam profile used for data exfiltration
These URLs align with known LummaC2 campaigns and are likely used for payload staging, configuration retrieval, or stolen data exfiltration.

#### System Profiling via WMI
Multiple decoded and tight strings show the malware is designed to query host system information using WMI classes, such as:

SELECT * FROM Win32_OperatingSystem
SELECT * FROM Win32_VideoController
SELECT * FROM Win32_BIOS
These queries allow the malware to build a system fingerprint, which is typically used to identify sandbox environments or tag unique victims.


#### Targeted Credential and Browser Artifacts
- Several strings indicate explicit targeting of browser-stored credentials:
Login Data, logins.json, key4.db, cookies.sqlite, Web Data, formhistory.sqlite, places.sqlite, and /Extensions/

- Firefox-specific artifacts like prefs.js, moz-extension+++, and ^userContextId=4294967295\idb
- Chrome-specific: \Local State, chrome.dll, and ChromeBuildTools
- Thunderbird profile path: %AppData%\Thunderbird\Profiles

These artifacts suggest support for multi-browser credential theft, including Chromium-based browsers, Firefox, and email clients.

#### Exfiltration Strategy and Format
FLOSS extracted strings such as:

- Content-Type: multipart/form-data; boundary=
- Content-Disposition: form-data; name="file"; filename="
- POST + application/x-www-form-urlencoded

These imply HTTP POST-based exfiltration using standard web form mimicking, likely to bypass simplistic firewall rules and content filters.



**Anti-VM and Sandbox Evasion**
Strings like VBox2DTn, reVM, and MMXe are indicative of:
- VM detection techniques, where execution flow may be altered or halted upon detecting virtualized environments (e.g., VirtualBox, VMware)

## Conclusion: Human + AI for Smarter Malware Analysis

This LummaC2 variant represents a sophisticated evolution of information-stealing malware, employing advanced obfuscation techniques to evade detection while maintaining powerful data theft capabilities. The combination of control flow manipulation, dynamic API resolution, and multi-stage payload execution makes it particularly challenging to analyze statically.
The malware's primary focus on credential theft, and system profiling aligns with the broader trend of financially motivated cybercrime. The techniques observed in this sample suggest that the operators are experienced and have invested significant resources in developing evasion capabilities.
In this project, I explored how combining AI-assisted tools like GhidraMCP with traditional static and dynamic analysis methods can improve the speed and depth of malware research. While human expertise is still key to understanding intent and behavior, AI can help automate repetitive tasks and highlight important patterns. Together, this approach makes malware analysis more efficient and insightful, showing the real value of using human and machine strengths side by side.
