## [](#header-3) So, what is MCP, exactly?

AI has come a long way—it can write, code, explain, and even reverse engineer. But one of the most exciting improvements lately is its ability to talk directly to other tools. That’s where Model Context Protocol (MCP) comes in.

MCP creates a bridge between AI systems and the tools or data they need. Here’s how it works in simple terms:
MCP Hosts are tools like Claude Desktop, IDEs, or any AI that wants to interact with your system.
MCP Servers are small programs that unlock specific abilities—like letting the AI read files, analyze memory, or control Ghidra.
MCP Clients manage the communication between the host and these servers, creating 1:1 channels.
Local Resources are things on your own machine (files, memory, databases) that the AI can securely access.
Remote Resources are things online—like APIs or external services—that MCP servers can reach out to.

I’ll walk through how I used this human–AI collaboration to analyze Lumma Stealer—from static analysis in Ghidra, to runtime behavior monitoring with tools like ProcMon. The goal isn’t to replace the analyst—but to show how much more efficient, insightful, and enjoyable reverse engineering can be when you have AI contextually aware of the binary you're working on.


### [](#header-3) We will start with GhidraMCP analysis to examine the malware statically;
A comprehensive examination of a sophisticated information stealer malware, identified as a variant of the LummaC2. The specimen employs multiple layers of obfuscation, including control flow manipulation, dynamic API resolution, and multi-stage payload unpacking.

The malware's primary objective is information theft, targeting:
- Browser credentials and cookies
- Clipboard contents
- Desktop screenshots
- System profile information


### [](#header-4) Key technical aspects include:

- Sophisticated control flow obfuscation using dispatcher blocks
- Hash-based API resolution to avoid static detection
- Multi-layer anti-analysis techniques targeting debuggers and virtual machines
- Extensive in-memory operations to minimize disk artifacts
- Custom encryption routines for both code and data


The binary's low function count (29) relative to its size suggests heavy obfuscation, which is confirmed during deeper analysis. The large number of defined data items (6470) indicates the presence of lookup tables used in the obfuscation mechanisms.

#### Import Table Analysis


The import table provides the first glimpse into the malware's capabilities:

**Process Operations**
- `CreateThread`, `GetCurrentProcessId`, `GetCurrentThreadId`, `ExitProcess`

**GUI and Screen Capture**
- `BitBlt`, `CreateCompatibleBitmap`, `CreateCompatibleDC`, `GetDC`
- `GetSystemMetrics`, `GetWindowRect`

**Clipboard Access**
- `CloseClipboard`, `GetClipboardData`, `OpenClipboard`

**COM/OLE Functions**
- `CoCreateInstance`, `CoInitialize`, `CoInitializeSecurity`
- `CoSetProxyBlanket`, `CoTaskMemAlloc`, `CoTaskMemFree`
- `CoUninitialize`, `VariantInit`, `VariantClear`

**File System Access**
- `SHGetFileInfoW`, `SHGetSpecialFolderPathW`, `GlobalLock`, `GlobalUnlock`

These imports clearly indicate the malware's information-stealing capabilities, particularly the combination of screen capture, clipboard monitoring, and COM functionality (commonly used for browser data access).

### [](#header-3)  Running **SharpHound** on the Target Machine

Now, here’s where things get interesting. BloodHound itself doesn’t collect AD data, that’s where `SharpHound` comes in.

SharpHound has two versions:

EXE version (SharpHound.exe)
PowerShell version (SharpHound.ps1)
 

Once SharpHound finished running, I had a zip file containing multiple JSON files, each representing different AD objects:
I then imported this zip into BloodHound’s GUI by simply dragging and dropping it in.
At this point, BloodHound started parsing the relationships and I could finally visualize attack paths within my test AD environment.

<img width="360" alt="1" src="https://github.com/user-attachments/assets/4165b3d3-7fe4-4820-885e-1b0192e3247e">



*   After collecting data with SharpHound, simply drag and drop the ZIP file containing the JSON data into the BloodHound GUI for analysis.

> After dragging and dropping the collected data into BloodHound, you might encounter an "Incompatible Collector" error. This usually happens due to a version mismatch between the SharpHound collector on the target machine and BloodHound on your analysis machine.Additionally, some folks report that newer BloodHound versions require running the .exe version of SharpHound instead of the .ps1 script. Using the PowerShell version may also trigger the "Incompatible Collector" error.

>
> SharpHound can run on a non-domain joined machine. This is possible when using the `/NetOnly` flag with runas or by passing valid domain credentials to collect AD data remotely. (Reference:https://www.ired.team/offensive-security-experiments/active-directory-kerberos-abuse/abusing-active-directory-with-bloodhound-on-kali-linux)

```
runas /netonly /user:hackland\mdunbar powershell
```

### [](#header-3) Detecting BloodHound in Your Environment

So far, we've talked about how BloodHound works and how attackers use it to map Active Directory. Now, let’s go over how I detected BloodHound activity in my lab and how you can spot it in your environment.

After running SharpHound on the compromised machine, I checked the Windows Security logs on my lab DC and found that my compromised user mdunbar was generating a high volume of Event ID 4662.

This event, which logs Directory Service Access, showed bulk LDAP queries targeting different AD objects.

User objects, Groups and OUs, Computers in the domain
Seeing these high-frequency LDAP read events from a regular user account is a red flag that BloodHound was running.

<img width="580" alt="1" src="https://github.com/user-attachments/assets/494f3bbe-1eca-4fca-ae38-30b69a5c4c77">


On the **network side**, monitor for:

`Unusual SMB Traffic – SharpHound may copy itself over SMB before execution.`

`High LDAP query volume in network logs.`

`Large numbers of LDAP queries from non-admin accounts.`

After reconnaissance with BloodHound, attackers typically progress to Active Directory exploitation, such as privilege escalation, credential theft, or delegation abuse. To detect and disrupt their next move, it's crucial to monitor security events related to account modifications, privilege escalation, and unauthorized directory access.
